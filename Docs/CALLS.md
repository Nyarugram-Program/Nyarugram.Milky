# Nyarugram 呼叫扩展与媒体契约

本文规定 Milky 适配服务的首期一对一电话能力。API 名称和媒体格式属于 Nyarugram 扩展设计，实际实现需要固定扩展版本并提供应用端调用示例。

## 目标

机器人应用可以向 Nyarugram 用户发起电话，接收来电、接听、拒接、挂断并查询状态。接通后可输入机器人音频，接收对端音频，用于播放、录音或上层语音处理。

首期语音验收要求真实双向声音。视频独立声明，在视频源、编码、传输及接收链路通过设备互通前，video=true 返回明确的未支持错误。

## 后端已有接口

| Protobuf 操作 | 编号 | 适配服务职责 |
|---|---:|---|
| request_call | 128 | 生成并持久化发起操作及随机 ID，提交被叫和真实 g_a_hash、协议能力 |
| received_call | 129 | 收到属于当前账号的来电后确认收到 |
| accept_call | 130 | 被叫验证邀请后生成 g_b，提交真实媒体协议能力 |
| confirm_call | 131 | 主叫校验并提交 g_a、密钥指纹和协商结果 |
| discard_call | 132 | 拒接、取消、挂断、超时和失败清理，保持终态幂等 |
| send_signaling_data | 133 | 转发媒体引擎生成的不透明信令，遵守实际大小限制 |
| get_call_config | 134 | 读取媒体引擎配置，校验并限制其使用范围 |
| save_call_debug | 135 | 仅按实际后端语义提交受限诊断，移除秘密与媒体内容 |
| get_dh_config | 136 | 获取并验证既有通话密钥协商参数 |

电话状态及信令通过 get_difference 中的 phone_call 和 phone_call_signaling 更新接收。通话以 call_id 和 access_hash 关联，禁止把业务会话 ID、消息 ID 和呼叫 ID 混用。

对外 get_call 从已验证的本地通话投影及最新差分取得状态。需要新增查询能力时通过后端 Protobuf 扩展解决，禁止访问已弃用的 REST 通话入口。

## 对外控制扩展

扩展统一使用 POST /api/{action}、Milky 鉴权及响应外壳。请求和响应维护明确 JSON Schema，并通过 nyarugram_get_capabilities 声明扩展版本。

| 扩展 API | 主要输入 | 主要结果 |
|---|---|---|
| nyarugram_resolve_username | username（支持 @ 前缀） | 稳定 user_id、规范 username |
| nyarugram_start_call | user_id、video、持久幂等 request_id | 适配服务 call_id、当前状态 |
| nyarugram_accept_call | call_id、request_id | 当前状态及媒体准备状态 |
| nyarugram_end_call | call_id、reason、request_id | 幂等终态或待确认状态 |
| nyarugram_get_call | call_id | 方向、对端、状态、时间、结束原因及媒体状态 |
| nyarugram_open_call_media | call_id、输入/输出能力 | 绑定该呼叫的短期媒体访问凭据和端点 |

对外 call_id 是服务内持久化的不透明标识，绑定服务器、账号、登录代际和后端 call_id。access_hash、私钥及内部令牌保留在适配服务中。

- start_call 幂等键复用时必须验证被叫、video 和相关选项一致。结果未知时复用原后端随机 ID 对账。
- end_call 支持 hangup、missed、busy、disconnect 等明确原因，按现有协议权限与方向映射。普通应用不能修改不属于自身账号的通话。
- 默认人工或应用显式接听。自动接听作为可配置策略，明确允许的来电范围。
- 同一账号按后端规则保持占线约束。遇到 busy 返回可识别的业务错误，不能遗留阻塞下一次拨号的本地状态。

## 扩展事件

通过 /event 推送下列扩展 event_type，包含稳定 event_id、call_id、账号、对端、方向、状态版本和时间。

- nyarugram_call_incoming 表示新的有效来电。
- nyarugram_call_state_changed 表示响铃、接听、协商、接通或结束变化。
- nyarugram_call_media_ready 表示媒体模块可以接收应用音频并输出对端音频。
- nyarugram_call_media_closed 表示该呼叫媒体已关闭，包含明确原因。

同一事件重投保留 event_id。应用可以依据状态版本丢弃迟到事件。标准 Milky 应用对这些事件的处理方式要在兼容性测试中验证，并提供调用扩展所需的 SDK 或示例。

## 通话状态与清理

适配服务区分 incoming、outgoing、ringing、accepted、negotiating、active 和终态 ended/failed，并保留后端原始状态及原因供诊断。

1. 同步取得有效来电，校验账号和权限，发送 received_call，持久化并推送来电事件。
2. accept_call 和 confirm_call 驱动密钥及协议协商，启动真实兼容引擎，按后端要求转发信令。
3. 后端 active、引擎连接成功、输入输出可用分别记录。达到真实媒体就绪条件后才发 media_ready。
4. 任一终态停止音频、媒体端点、引擎、重试和定时任务，撤销短期令牌，并释放挂起和占线标记。
5. 重复终态、迟到 received/accept、旧 call_id 和旧会话回调不能关闭新电话或恢复旧电话。
6. 服务或引擎重启后，以后端状态对账。无法恢复原媒体时明确结束或失败，保证账号可以再次接打。

### 运行期媒体故障

媒体已就绪后，代理进程退出、控制连接 EOF、读写失败或引擎报告 `failed` 都可能使通话失去媒体。适配服务按以下规则处理：

- `IMediaSession.Completion` 在会话结束时完成一次：主动关闭返回 `null`，异常终止返回 `MediaFault`。故障通知不得等待会话所有者释放资源。
- 媒体启动失败（`StartAsync`、`WaitForReadyAsync` 抛错或超时）仍走有界重试；重试耗尽后把媒体标为失败。已就绪后的故障不原地重试，直接结束通话。
- 故障处理在通话锁内检查账号/登录代际、引擎当前实例和通话终态。只有 `engine.Find(call_id)` 仍等于故障会话时才生效，旧代理迟到退出不会关闭替换后的媒体。
- 生效时先停止该通话的信令队列，再以 `failed` 终态在同一个数据库事务中写入 `media_state=closed` 和 `nyarugram_call_media_closed`，随后释放音频通道、控制 socket、子进程、媒体令牌和任务。
- 后端 `discard_call` 暂时失败时记录 `pending_end_reason=failed` 与对账退避，由维护任务继续释放占线；适配进程不退出，双方后续可以重新拨号。
- 数据库暂时不可用时，故障处理先停止媒体、信令队列、进程、socket 与音频任务，再把收尾意图保留在内存待办中，由 `CallFaultFinalizer` 以 1 秒起的退避自动重试；恢复后完成 `failed`、`media_closed`、媒体凭据撤销与后端线路释放。
- 收尾先在库中写入 `reconcile_state=pending`，再做终态事务。终态提交成功但撤销凭据或释放线路失败时，重试从已提交状态继续；`media_closed` 只由实际应用的状态版本产生，重复执行不会重复终态或事件。
- 内存待办绑定服务器、账号、登录代际、call_id 以及具体的媒体/信令实例；账号切换或实例被替换时直接丢弃。进程重启不重放内存待办，而由启动对账处理上一实例遗留的通话；因此重启边界是"旧实例一律结束/失败"，不是"恢复旧媒体"。
- 挂断与故障并发时依靠状态版本只允许一个终态事务提交；另一路径只做幂等资源清理，不重复产生终态事件。

### 出站信令投递

引擎信令在媒体读循环中产生，不能在该线程上等待后端。适配服务为每个媒体实例建立一个独立的有界队列（`SignalingRelay`）：

- 入队不阻塞 PCM 读取；单个 worker 按入队顺序发送，只有可恢复错误（未知结果、可重试错误、HTTP 0/408/429/5xx、IO/Socket/超时）才重试，指数退避有上限。单条信号最多 `signaling_max_attempts` 次；队列满、过期、永久失败或耗尽都会结束该通话并走统一的失败/释放路径。
- 每次发送前都检查条目的剩余有效期；重试等待不超过剩余时间；在途发送由单调递增的剩余有效期约束本地等待，超时即取消并报告 `signaling_expired`。
- 有效期使用 `Stopwatch` 单调时钟，不受系统时间调整影响。区分主动停止/账号失效（静默停止、不结束新通话）、条目过期、永久失败与重试耗尽；失败通知保持幂等。
- 已发出的请求可能在服务端已生效，本地取消不保证撤销提交，因此该边界仍按至少一次处理并在文档与日志中注明。
- 队列绑定服务器、账号、登录代际、call_id、信令绑定和具体媒体实例。挂断、退出、账号切换、媒体替换或对账释放都会停止旧队列；媒体实例被替换后，旧实例的回调与旧队列的失败回调都会因绑定校验失败而被丢弃。
- 后端 `send_signaling_data` 没有幂等键。若响应丢失但后端已提交，重试会以相同负载重复投递，这是可接受的至少一次边界；tgcalls 的 SDP/ICE 信令可容忍重复。适配服务不宣称严格恰好一次。
- 队列是内存队列：进程重启时队列内容丢失，启动对账把旧实例的通话结束或失败，新进程不会把旧媒体实例的信令投递给新实例。该恢复边界在每次重启后都必须通过对账完成。

## 媒体实现要求

- 与当前 Android VoIPService 使用的实际通话引擎、库版本、协议层和信令兼容。能力来自实际链接和测试通过的版本，禁止硬编码宣称支持不存在的引擎版本。
- 获取并验证 DH 参数、对端公钥及密钥指纹，使用成熟密码学实现和安全随机数。私钥及音频内容不进入普通持久化或日志。
- 验证后端下发的 STUN/TURN、P2P 策略和媒体端点，凭据受限使用。媒体路径覆盖 P2P 与部署者配置的 TURN 中继。
- 引擎绑定或独立媒体子进程需固定来源、版本、许可证和构建校验值，包含异常退出、超时和资源释放处理。
- HTTP 控制和 WebSocket 事件不能替代实际加密媒体传输。不能只模拟来电、返回 active 或转发任意 SDP 即宣称通话可用。

## 应用音频接口

首期提供独立媒体 WebSocket /nyarugram/calls/{call_id}/media，使用该呼叫短期媒体凭据。媒体端点和普通 Milky 事件连接分别鉴权。

- 基础应用格式采用 PCM signed 16-bit little-endian、48 kHz、单声道、20 ms 音频帧，每帧 1,920 字节。入口格式和引擎内部编解码分别协商或转换。
- 首帧交换媒体协议版本、输入/输出方向和格式，随后双向传输带序号和时间戳的二进制音频帧。实现时固定帧头 schema、最大帧长及错误响应，写入版本化契约。
- 输入用于机器人播放，输出为对端接收音频。使用有界缓冲、时钟、静音、背压与明确的丢帧策略，不能无限积压。
- 后端通话结束即撤销媒体凭据和连接。旧令牌、其他账号、其他 call_id、过期时间和重放均需校验。
- 上层可接入 TTS、ASR 或其他机器人音频源。基础双向语音不依赖付费 AI 服务，测试使用本地确定性音频源和接收器。

## 必须执行的验收

| 场景 | 验收要求 |
|---|---|
| 机器人呼叫手机 | 手机响铃，接听后播放机器人音频，机器人收到手机声音 |
| 手机呼叫机器人 | 收到来电事件，显式接听后双向音频可用 |
| 响铃阶段拒接 | 任意一方拒接后，双方立即可以重新发起通话 |
| 取消、忙线和超时 | 状态和原因一致，无挂起标记及资源泄漏 |
| 丢响应与重复请求 | 同 request_id 保持同一通话，重复挂断保持终态 |
| 迟到事件和账号变化 | 旧事件不改变新通话，退出账号后资源和权限释放 |
| 网络和进程异常 | 断线、引擎退出、服务重启后明确恢复或终止，随后可重拨 |
| 媒体与权限 | P2P/TURN 各自验证，媒体凭据和访问权限拒绝用例通过 |
| 音频内容与时钟 | 双向已知音频内容、持续传输、静音和有界延迟验证通过 |

后端信令测试、宿主密码学测试和模拟媒体分别记录。真实手机到适配服务的双向音频是独立必测项。

## 实现状态

首个版本的帧格式与端点约定见 [媒体 WebSocket 契约](MEDIA-PROTOCOL.md)。

当前构建包含与 Android `VoIPService` 相同的 tgcalls 引擎实现 `tgcalls::InstanceV2Impl`：

- 引擎以独立子进程 `milky_media_agent` 运行（Linux x86-64），通过 127.0.0.1 随机端口的长度前缀控制帧接收启动参数、对端信令和 PCM，进程就绪后打印 `READY <port>`。适配服务崩溃后代理检测控制连接断开并退出。
- 注册版本 `13.0.0` 与 `12.0.0`，`MaxApiLayer=92`、`MinLayer=65`；生产 Android 客户端使用 `13.0.0`。
- 密钥沿用后端 2048-bit DH 参数（p=`CallService.DhPrime`，g=3），共享密钥经 SHA-256 校验后作为 tgcalls 256 字节 authKey；指纹为 SHA-1 尾部 8 字节的有符号小端值。
- 信令完全复用引擎生成的加密 SCTP/mtproto 负载，经后端 `send_signaling_data` 与差分投递中继，不自行构造或解析 SDP。
- 应用音频固定为 PCM S16LE、48 kHz、单声道；采集 10 ms，收发帧 20 ms。`media_ready` 只在信令 `established` 且已收到至少一帧对端音频后发出。
- 引擎连接超时从 tgcalls 原生 20 秒调整为 45 秒以覆盖适配器中继；初始化/接收超时各 60 秒。

已验证（2026-11-08，隔离 `NewStoragePrimary` + `RelationalBackend` PostgreSQL 权威后端 + 两个独立适配实例）：

| 场景 | 结果 |
|---|---|
| P2P 双向音频（适配实例 A↔B） | 通过，双方 RMS 375/647，A 收到 660 Hz、B 收到 440 Hz（能量比 > 4 万，排除静音/串音/本回环） |
| 媒体进程内自测与双进程桥接 | 通过，帧数与过零率符合 440/660 Hz 输入 |
| 接通后仅强杀媒体代理（适配进程存活） | 通过：持久化 `failed/closed/closed`，消费者收到 `nyarugram_call_media_closed`；双方重拨后双向音频恢复 |
| 代理退出与挂断并发 | 通过：只有 1 个终态事件和 1 个 `media_closed` 事件；线路随后可再次拨打 |
| 媒体故障后后端 discard 暂时失败 | 宿主回归通过：`pending_end_reason=failed`，维护任务自动对账后释放 |
| 出站信令瞬时 500、响应丢失、顺序、重试耗尽、队列上限/过期/取消 | 宿主回归通过（真实后端故障注入见交付报告边界） |
| 通话中强杀主叫适配进程后重启 | 通过，被叫看到 `ended/disconnect`，重拨后双向音频恢复 |
| 拒接后重拨、取消、忙线、超时 | 通过（见交付报告） |
| 后端进程重启、适配器状态 PostgreSQL 重启、后端业务 PostgreSQL 重启 | 通过：每次恢复后仍可收发消息并完成双向已知音频通话 |
| TURN 中继 | 未验证：隔离后端 `Rtc:IceServers` 为空，仅 P2P |
| Android 真机双向音频 | 未验证：当前环境无连接设备（`adb devices` 为空） |
| 视频 | 未实现，发起前拒绝 |

未完成项不得以宿主测试或实例间互通替代。真机验收仍需：机器人呼手机、手机呼机器人、SDP/ICE 在真实网络下的 P2P 与 TURN、弱网与断网恢复、双方重拨。

## 仅响铃提醒模式

设置 `media.engine=ring_only` 可通过真实后端呼叫邀请触发手机来电提醒，无需原生媒体代理。用户拒接、主叫取消和后端超时沿用现有终态处理；被叫接听后主叫在媒体确认前主动挂断。该模式声明 `calls.ring_only=true`、`calls.voice=false` 和 `media_available=false`，不提供音频或接听能力。手机是否显示全屏来电仍取决于 Android 客户端、通知和全屏提醒权限，以及系统设置。
